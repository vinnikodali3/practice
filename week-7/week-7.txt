That's why we have a separate warehouse
Q2. 
First difference — storage model. OLTP uses row-based storage, optimised for writing and reading one row at a time. OLAP uses columnar storage, optimised for reading specific columns across millions of rows.
Second difference — what they're optimised for. OLTP is built for fast inserts, updates, and single-row lookups like processing a payment. OLAP is built for heavy aggregations and analytical scans like calculating total revenue by region for the whole year.
Third difference — data model. OLTP tables are highly normalised 3rd normal form to avoid duplication and support fast writes. OLAP tables are denormalised star schema with wide fact tables to avoid joins at query time and make reads faster.
Q3
OLTP database has a fixed amount of CPU, memory, and disk I/O. When a billing transaction runs like inserting a new invoice it uses a small slice of those resources and finishes in milliseconds.
But when an analyst runs a heavy aggregation like summing all invoices for the past year that query grabs a large portion of the same resources. Now the billing transactions have to wait in line. Processing that used to take milliseconds might take seconds or even time out.
In a busy system, if multiple analysts do this at the same time, invoice processing can effectively stop. This is called resource contention, and it's the core reason you need a separate warehouse for analytics.

Task - 2
Q1.
"Imagine a spreadsheet with 50 columns and a billion rows. In a row-based database, all 50 columns of row 1 are stored together, then all 50 of row 2, and so on. If I run a query that only needs the Name column and the Amount column, the database still reads all 50 columns for every row and throws 48 away. That's a lot of wasted work."
In a columnar store, think of the spreadsheet stored sideways. Column A all the names is in one file. Column B all the amounts is in another. Columns C through Z are in separate files. If my query only needs columns A and B, it reads just those two files. It never touches columns C through Z.
On a billion-row table with 50 columns, that's the difference between reading 50 billion values versus 2 billion values. 25 times less data 25 times faster and 25 times cheaper for that query.

Q3.
In a traditional database, the machine that stores your data is also the machine that processes your queries. They're tied together. If you need more processing power, you have to upgrade the whole machine, even if the data size hasn't changed
In modern cloud warehouses like BigQuery, Snowflake, or Redshift Serverless, compute the processing power and storage where the data lives are completely separate. You can scale them independently.
business benefit: say nobody queries the warehouse for 8 hours overnight. With compute and storage separated, you turn the compute off completely. You only pay for storage during those hours. In the old model, your database server is running and costing money 24 hours a day whether it's doing work or not. That's a significant cost difference at scale

Q1.
Staging is a landing zone. Its only job is to receive data from the source without losing any of it. The moment you put a typed column in staging say a DATE column — you're making a promise: every value must be a valid date. If the source sends '2024-99-99', the load fails with a type error. Your whole pipeline stops
By using VARCHAR for everything, we remove that risk. Whatever the source sends valid date, broken date, null, garbage string it gets stored. The load always succeeds. We deal with data quality in the curated layer, where we have proper validation logic

Q1.
Redshift table
CREATE TABLE fact_billing
(
invoice_id VARCHAR(50),
customer_id VARCHAR(50) DISTKEY,
invoice_amount DECIMAL(12,2),
invoice_date DATE
)
SORTKEY(invoice_date);

BigQuery 
CREATE TABLE fact_billing
(
invoice_id STRING,
customer_id STRING,
invoice_amount NUMERIC,
invoice_date DATE
)
PARTITION BY invoice_date
CLUSTER BY customer_id;
In Redshift, I use DISTKEY and SORTKEY to optimize joins and filtering. In BigQuery, I use PARTITION BY and CLUSTER BY because Google automatically handles data distribution. Redshift requires cluster management, while BigQuery is fully serverless.
Q2.
BigQuery is a serverless warehouse. Google automatically distributes data across its infrastructure. Since data distribution is handled internally, users do not need to configure DISTKEYs like in Redshift.

Task - 8
Q1.
-- ══ STEP 1: Load staging (full load — staging is small, rebuilt every run) ══
TRUNCATE TABLE stg_billing_raw;
COPY stg_billing_raw
FROM 's3://data-lake/billing/2024-01-15/'
IAM_ROLE 'arn:aws:iam::123456789:role/RedshiftS3Role'
CSV IGNOREHEADER 1;

-- ══ STEP 2: Validate before touching curated ══════════════════════════════
SELECT
    COUNT(*)                                                AS total_rows,
    SUM(CASE WHEN invoice_id     IS NULL THEN 1 ELSE 0 END) AS null_ids,
    SUM(CASE WHEN invoice_amount IS NULL THEN 1 ELSE 0 END) AS null_amounts
FROM stg_billing_raw;
-- If null_amounts / total_rows > 0.01 → STOP pipeline, raise alert

-- ══ STEP 3: Incremental MERGE into curated ════════════════════════════════
MERGE INTO fact_billing AS target
USING stg_billing_raw AS source
ON target.invoice_id = source.invoice_id
WHEN MATCHED THEN
    UPDATE SET
        invoice_amount = CAST(source.invoice_amount AS DECIMAL(12,2)),
        invoice_date   = CAST(source.invoice_date   AS DATE)
WHEN NOT MATCHED THEN
    INSERT (invoice_id, customer_id, invoice_amount, invoice_date)
    VALUES (source.invoice_id, source.customer_id,
            CAST(source.invoice_amount AS DECIMAL(12,2)),
            CAST(source.invoice_date   AS DATE));

-- ══ STEP 4: Refresh reporting table (idempotent — delete then insert) ══════
DELETE FROM rpt_monthly_revenue
WHERE month = DATE_TRUNC('month', CURRENT_DATE);

INSERT INTO rpt_monthly_revenue
SELECT DATE_TRUNC('month', f.invoice_date) AS month,
       c.customer_segment,
       SUM(f.invoice_amount)               AS total_revenue,
       COUNT(DISTINCT f.customer_id)       AS active_customers
FROM   fact_billing f
JOIN   dim_customer c ON f.customer_id = c.customer_id
WHERE  f.invoice_date >= DATE_TRUNC('month', CURRENT_DATE)
GROUP  BY 1, 2;

Q3.
The reporting refresh is idempotent because it deletes the current month's records before inserting fresh data. Running it multiple times does not create duplicates or incorrect totals.
Q4.
If the MERGE runs twice with the same data, the result remains unchanged. Existing records are updated with the same values and new records are not inserted again. This makes MERGE safe and reliable for incremental loading.
